### NOTES
The key reduction is that the even-exponent condition forces every 400 number to be a perfect square. If N = p^{2a} q^{2b} with distinct primes p and q and a,b >= 1, then x = p^a q^b is an integer at most 10^6 and has exactly two distinct prime factors. Conversely, any x <= 10^6 with exactly two distinct prime factors produces a valid 400 number x^2. Therefore the problem over values up to 10^12 becomes a predecessor problem over bases x up to 10^6.

The core difficulty is not the number theory itself, but answering 2e5 predecessor queries quickly. We need a compact precomputation up to 10^6 and a fast way to find the largest valid base not exceeding floor(sqrt(A)). Important pitfalls include using floating-point square roots near 10^12, counting total prime factors instead of distinct prime factors, accidentally allowing one prime factor or p = q, missing the boundary value 10^6, generating duplicates, and Python memory/time issues for large arrays or repeated big-integer operations.

### NEXT
- Use a smallest-prime-factor sieve up to 1,000,000 to compute the number of distinct prime factors for every base. Keep bases with count exactly 2 in an ascending list. For each query, take the integer square root B of A, binary search the list for the largest base <= B, and square it. Pitfalls: the distinct-count recurrence must not increment when the same prime divides the quotient again; the list must include 6 and 1,000,000; binary search must handle B below the first valid base even though constraints avoid it; storing bases rather than squares keeps numbers smaller and makes the square step explicit.

- Build a direct predecessor table over the base range: after marking valid bases, fill an array where each position stores the nearest valid base at or before it. Then each query is answered in constant time by looking up B = integer square root of A. Pitfalls: a Python list of one million integers may use significant memory; a compact integer array or a sorted-list fallback may be preferable; the table must be filled correctly through the invalid prefix below 6; this approach trades memory for query speed.

- Enumerate prime-power pairs directly: sieve primes up to 1,000,000, iterate smaller prime p only up to below 1000, generate powers p^a, and for each power generate powers q^b for primes q > p while p^a q^b <= 1,000,000. Store the square of each product, sort and optionally unique, then binary search for queries. Pitfalls: both exponents must be at least 1; q must be strictly larger than p; the outer p bound follows from p < q and pq <= 1,000,000; generation order is not sorted; large q values near 500,000 must be available; boundary cases such as 2^6 * 5^6 = 1,000,000 must be included.

- Use a bitset of valid bases and a word-level predecessor search. Mark bit x if x has exactly two distinct prime factors. For a query limit B, find the highest set bit not exceeding B by inspecting the current word, masking off higher bits, and if empty using a summary bitset of nonempty words to jump backward. Square the found index. Pitfalls: naive big-integer masking per query may allocate large temporary integers and be too slow; scanning words downward without a summary can be slow if gaps are large; masking and bit-index arithmetic are easy to get wrong; implementation is more complex than a sorted list but memory is small.

- Process queries offline: sort queries by their square-root limit B, generate or sort all valid bases in increasing order, scan both lists, and maintain the last valid base seen to assign answers. Pitfalls: original query order must be preserved via indices; sorting 200,000 queries adds overhead but is usually fine; if the valid bases are generated unsorted, they must be sorted first; this avoids per-query binary search but is less straightforward than online binary search.

- For each query, search downward from B = integer square root of A until a base with exactly two distinct prime factors is found, using a precomputed factor-count array. Pitfalls: the worst-case gap between valid bases is not given and could make this too slow for many adversarial queries; it may be acceptable only if combined with a proven small maximum gap or a fallback to a predecessor structure; generally this is the least robust approach.

- Treat each prime power p^a <= 1,000,000 as an item with value and prime label, and answer each query as a constrained two-item product problem: choose two items with distinct primes whose product is at most B. Use range maximum or persistent segment tree structures over prime labels to find the best compatible second item for candidate first items. Pitfalls: the distinct-prime exclusion makes the query nontrivial; iterating over many first prime powers per query may be too slow; building and querying 2D structures is complex and likely overkill compared with precomputing all products or bases.
