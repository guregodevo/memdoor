# release-notes

Writes a release's notes — Added, Changed, Fixed — from the commits since the tag before it.

`log` takes the range: from the newest tag before the release to the release — the partition when it names a tag or a commit, else HEAD — fetching the history and tags a shallow checkout lacks, and keeps every commit message in `.memdoor/runs/release-notes-<partition>.log`. `notes` reads them (and `git show` for a commit whose message does not say what changed) and writes `.memdoor/runs/release-notes-<partition>.md`: a `## <version> — <date>` heading, then **Added**, **Changed** and **Fixed**, each item one sentence a person using the project notices. Nothing is committed or published; the file is ready for a changelog or `gh release create --notes-file`. Run it with `memdoor workflow run release-notes --partition v1.2.0 --wait` (no partition: everything since the last tag), or in GitHub Actions on a tag push with `uses: guregodevo/memdoor-action@v1`, `workflow: release-notes` and `partition: ${{ github.ref_name }}`. Needs a model on your key.

On a slow model, set `MEMDOOR_LEAN=1` (the GitHub Action sets it with `local-model:`, a model on the runner's CPU): `notes-lean` writes the notes instead, in one model call with the commit log in the prompt and thinking off, no tools and no loop — so it never reads `git show`; it writes only from what the log says. `log` then also keeps a short log, `.memdoor/runs/release-notes-<partition>-lean.log`: the subjects and the first two lines of each body, at most 300 commits, small enough for a CPU to read. Both steps write the same file, `.memdoor/runs/release-notes-<partition>.md`, in the same shape; exactly one runs.
