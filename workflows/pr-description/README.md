# pr-description

Writes a pull request's description from the change itself. `diff` takes the change the way pr-review's diff step does: in a GitHub pull request, the PR against its base branch; elsewhere, the branch against the default branch, or the last commit (with uncommitted edits), with a sensible fallback when a GitHub-only input is missing. `commits` takes the commit messages on the change's side. Then one of two steps writes `.memdoor/runs/pr-description-<partition>.md`: a one-line title, then **What** (what changes, for a reviewer), **Why** (from the commits and the code; "not stated" rather than invented), **How to test** (commands someone can follow), **Risk** (what could break, or "low" and why) — plain and short, no marketing words. It changes no project file. Run it with `memdoor workflow run pr-description --wait`, or in GitHub Actions with `uses: guregodevo/memdoor-action@v1` and `workflow: pr-description` (check out with `fetch-depth: 0` or the default; the base branch is fetched). Needs a model on your key.

On a slow model, set `MEMDOOR_LEAN=1` (the GitHub Action sets it with `local-model:`, a model on the runner's CPU, e.g. an 8B on 4 CPUs): `describe-lean` writes the description instead, in one model call with the diff and the commits inlined in the prompt and thinking off, no tools and no loop. A CPU reads a few thousand tokens a minute, so a big diff is slow.

Run it on `pull_request`, never `pull_request_target`: GitHub gives a fork's pull request no secrets, so a stranger's code never runs next to your key; `pull_request_target` runs their code with your secrets.
